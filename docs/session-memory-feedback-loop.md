# 会话回收反馈循环与热更新正文留存

日期：2026-10-29。前序：[预算准入](session-memory-admission.md)、[内存约定](session-memory-contract.md)。

## 确定性故障

8MiB准入修复后，用户仍反馈直接打开会话页面后内存持续增长并卡顿。本轮不把前序预算修复等同于现场问题已解决，而是分别检查持续更新和热更新留存。

已确认的回收反馈循环：单条3MiB的合法图片URL，其显示估算约6MiB，低于默认8MiB；当浏览器JS堆压力触发4MiB回收预算时，不能通过截断URL缩小它。`compactCodexTranscript`没有实际修改事件，却返回了新的数组包装；`releaseSessionMemory`据引用变化重新发布events；自身订阅随即安排250ms后的回收。没有任何新消息或用户操作，也会反复更新。

先红后绿的真实代码单测：固定300MiB压力分支、相同附件和原阈值，推进2100ms时旧实现发布9次完全相同正文；修复后发布0次，仅保留原5秒watchdog，不再排自激250ms任务。此处300MiB仅是测试提供的压力读数，没有为测试实际申请300MiB。

修复有两层：compactor在所有事件对象及顺序均未变化时复用原数组；governor也忽略只有包装不同的结果。没有调大预算、截坏附件、丢失身份或关闭正常回收。这能消除该路径的重复计算和渲染，不据此声称所有内存增长均来自它。

Chromium真实定时器回归`tests/e2e/session-memory-feedback-loop.spec.ts`运行2300ms以上，同样0次发布且事件/数组身份保持。该用例在独立空白探针页加载实际模块，不加载任务、不渲染测试图片；它证明真实浏览器定时器下的状态稳定性，不是整个聊天界面的长期RSS验收。

## Codex store 的真实热更新留存

旧 `useCodexStore` 每次模块重执行都会创建新 Zustand store。旧 ES 模块命名空间仍可通过导出持有旧 store，旧 store 的闭包再持有完整 events；只清理恢复缓存 Map 不能覆盖这条路径。它要求开发热更新发生，不能解释没有 HMR 的独立长期 RSS 红灯，也尚未从用户原标签页确认热更新次数。

隔离真实 Vite 对照使用产品 store 源码、真实 Zustand vanilla 与最小三个 slice；React hook 包装为空，因此物理留存结果只验证 store 生命周期。每代放入不同的 2MiB 正文，三次功能性依赖更新后，四个旧/新 store 均存活且互不相同；诊断 GC 后 `backingStorageSize` 2,289,136→8,588,116 bytes（+6,298,980），renderer RSS 94,605,312→104,288,256 bytes。JS used heap 仅约1.36→1.40MB，不能只据该字段排除大字符串留存。

现首次模块求值即在 `import.meta.hot.data` 注册同一个 store；热更新复用其数据与订阅，并重新绑定新版 slice actions、仅补缺失默认字段。不能把旧 state 快照留在模块顶层，也不能仅复用旧动作而让后续修复失效；生产无 HMR 时保留正常独立初始化。

回归 `tests/e2e/session-store-hmr.spec.mts` 包括三次功能性 slice 更新和两次 store 更新：六个模块导出都指向同一个 store、只保留当前 2MiB 正文，动作版本确实更新，当前线程、busy、排队数据及 localStorage 草稿保持，无刷新和页面异常。五次更新后 backing storage 2,294,735→2,322,963 bytes（+28,228）；同前三次更新只增加17,748 bytes。renderer RSS 94,691,328→98,217,984 bytes。这是显式 GC 下的因果留存诊断，不能称为全页面自然回收或长期 RSS 达标。另有真实 React/Zustand 单测核对已挂载消费者跨更新保持数据并取得新版动作。

修复前已经积累的旧模块实例无法由新代码可靠反向枚举；用户手动正常刷新一次才能清除旧代。这不是周期性刷新方案，不清空草稿/原生历史，不停止或重启任务。
