# 保留原版 Codex 扩展的可行性评估

2026-10-12。状态：首次架构评估，尚未实施迁移或完成原版扩展双面板运行验收。本次只读取现有实现、固定 VSIX 与官方资料，没有安装／升级扩展、修改原包、重启宿主或接管会话。云任务开发继续暂停。

**接口逆向后的修订**：后续已发现指定会话URI、owner discovery及17个follower请求，公共输入可以尝试通过私有IPC交给原会话owner；原版导航也支持既有会话文本预填。“缺少公开接口”不能解释成“没有可调用接口”。优先候选进一步明确为原包＋真实宿主＋伴随扩展＋版本化IPC适配器；实际草稿/附件双向同步、完整宿主运行与升级兼容仍待验收。详见 [接口逆向与复评](native-extension-interfaces.md)。下文保留首次评估的证据边界。

## 结论

用户希望保留原插件属性、获得原生聊天体验，并独立升级插件。最符合这一目标的候选方案是 **未修改的官方 Codex 扩展 + 完整 VS Code 宿主 + 独立 Coding Kanban 伴随扩展／外层工作台**。

桌面原生 VS Code 中运行扩展具备明确基础；在本项目的 code-server／OpenVSCode Server 中运行，仍需验证具体宿主版本、提议 API、Webview 资源和登录回调兼容性，不能由“支持 VS Code 扩展”推断全部可用。

此路线可以降低聊天正文、输入框、菜单、审批等原生 UI 的追版成本，但有产品取舍：保留原生输入框与宿主布局较容易；继续保留跨窗口公共输入框、任意外层会话卡片布局和外层精确会话控制，目前没有足够公开接口证据。独立升级表示包和代码可以分开发布，不表示任何版本组合都无需验证，也不表示更新不会要求宿主重载。

## 已核实的事实

1. 官方 [Open Source 清单](https://learn.chatgpt.com/docs/open-source) 明确列出 IDE extension 为 Not open source；CLI、SDK、App Server 等组件开源。公开 Codex 仓库的许可不能直接视为 VSIX 的源码许可。
2. 本地固定参考包为 `third_party/openai.chatgpt-26.51002.51308-linux-x64/extension`，版本 26.51002.51308。包内有打包后的 `out/extension.js` 和 Webview 资源，未发现 `.map` 文件；不是可直接维护的原始 TypeScript／React 工程。
3. 原包 `package.json` 使用 `main: ./out/extension.js`，没有 `browser` 入口，要求 VS Code `^1.96.2`；声明 `chatSessionsProvider`、`languageModelProxy` 两项提议 API。其实现使用 Node、原生 CLI 与 VS Code API。普通网页和仅有浏览器扩展宿主的 vscode.dev 不能直接承担这一宿主；带远程 Node 扩展宿主的方案另行验证。见 [Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host)。
4. 原包贡献 `chatgpt.newCodexPanel`，官方 [命令文档](https://learn.chatgpt.com/docs/developer-commands?surface=ide) 同样列出该命令。静态实现注册该命令并调用 `createNewPanel()`，经 `vscode.openWith` 打开 `chatgpt.conversationEditor`；另有 `editorPanels` 集合和 `createWebviewPanel`，说明多聊天面板有实际实现基础。尚未用该证据冒充多项目独立状态或真实双面板测试。
5. Webview 加载依赖宿主的 `asWebviewUri`、CSP、消息收发和持久状态。扩展导出入口为 activate/deactivate；所查激活函数未返回可供其他扩展使用的会话控制 API。已检查公开贡献命令，未找到公开的“向指定 thread 写入公共输入草稿／发送消息／订阅全部面板状态”接口。内部路由与消息协议不是公开兼容性承诺。
6. VS Code Webview 在独立上下文运行，由创建它的扩展持有消息通道；普通伴随扩展不能依靠标准 API 任意读取或改造另一扩展的聊天 DOM。见 [Webview API](https://code.visualstudio.com/api/extension-guides/webview)。
7. 当前项目已有 `VsCodeWebManager`、保留挂载的 VS Code iframe 和 `packages/codex-host-bridge`。现有桥读取编辑缓冲／选区、定位和显示 Diff，其服务及协议可以复用；该桥目前不提供原版 Codex 会话控制接口，也不等于原版 Codex 扩展完整运行验收。

## 候选路线比较

| 路线 | 原生聊天体验 | 原插件独立升级 | 对现有产品的影响 | 判断 |
| --- | --- | --- | --- | --- |
| 复制并修改 VSIX 打包代码 | 可从原版开始，但逐渐分叉 | 改动需随上游重新合并 | 改内部布局较自由，维护成本高 | 不符合优先目标 |
| 原版扩展 + 完整 VS Code 宿主 + 伴随扩展 | 使用实际原生 UI | 包可独立升级，宿主／伴随适配仍需回归 | 保留宿主与原生输入框；部分公共输入与外层布局需取舍 | 首选验证 |
| 不改 Webview JS，自己模拟其宿主消息协议 | 可以复用原版前端资源 | 私有协议每次变化都可能要改适配器 | 布局自由，但需补大量宿主语义与资源处理 | 技术候选，维护风险高 |
| 基于公开 App Server 自建 UI | UI 由我们维护 | 运行层可升级，官方 UI 不会自动跟进 | 保留现有公共输入、分屏及手机体验最容易 | 当前方案／回退路线 |

官方 [App Server](https://learn.chatgpt.com/docs/app-server) 提供认证、历史、审批和流式事件，适合自建产品；复用它本身不会把官方 IDE 界面带入网页。

## 推荐边界

外层工作台管理项目入口、工作区生命周期、窗口／网格容器、窗口组和版本选择。真实 VS Code 宿主运行未修改的 Codex 扩展；我们的伴随扩展只通过已公开的 VS Code API、Codex 命令和经过验证的桥接能力管理宿主操作。

同一工作区优先验证一个宿主中的多个原生 Codex 编辑器面板，避免每个会话都创建完整编辑器；跨项目验证独立工作区视图，再测宿主／进程是否可合理复用。将整个工作台装入外层 iframe 的网格具有实现基础，但每格包含完整编辑器，资源成本与窄屏可用性要单独验收。仅把 Codex 的内部 Webview 从宿主拆出并移入任意网页网格，属于另一条宿主适配路线，不能算标准伴随扩展能力。

原版扩展拥有其聊天发送、审批与会话写入链路。外层状态整合须找到明确支持的只读接口；不能在没有证据时假设可以连接它正在使用的 App Server，更不能让现有运行层与原插件同时取得同一 thread 的写入权。关注卡片、未读和审批汇总能否完整整合，仍是验证项。

多面板显示必须保持各自草稿、附件、滚动、线程与项目身份。隐藏、切换和移出关注集合不能隐式停止 Agent；宿主关闭／升级是否影响运行中的任务须实测。原插件自己的后台缓存与内存策略由它控制，不保证继承本项目已实现的正文回收保护。

手机可以访问带服务器 Node 宿主的网页，但“能打开”不能证明软键盘、触控、语音、权限弹窗或窄屏完整可用。首轮保留现有手机界面作为回退候选，不把桌面原生面板结论泛化为手机验收。

## 最小验证和采用条件

在独立项目、独立用户／扩展目录和可配置端口中进行，前端绑定 `0.0.0.0`，使用实际局域网 URL。正式 Agent、现有登录目录和编辑器窗口保持原样。

1. 安装未修改的固定官方 VSIX，记录版本／摘要，验证在所选 VS Code Web 宿主内真实激活、Webview 加载、资源、认证状态和登录回调。提议 API 的支持须记录；缺能力时明确降级或拒绝启动，不能偷偷补丁原包。
2. 用伴随扩展调用 `chatgpt.newCodexPanel`，打开两个原生聊天面板，验证分栏、不同会话草稿／附件、焦点、隐藏恢复和多项目归属。静态命令存在不替代行为验收。
3. 列出外层可以使用的公开操作与无法实现的操作，重点验证会话标识映射、只读状态、公共输入区、审批和关闭边界。若只能靠私有 DOM／消息补丁实现核心需求，重新评估这一方案是否仍满足独立升级目标。
4. 在测试会话上做真实发送、流式、审批、Diff、断线恢复；开发前先补对应红灯用例。测试不借用现有活跃 thread。涉及真实发送和破坏性操作时按已有授权及显式 UI 范围执行。
5. 测量两面板和更多面板的 JS 堆、renderer RSS、后台传输、切换耗时；手机软键盘／窄栏独立验收。不沿用自建 UI 的通过数字证明原插件稳定。
6. 保持伴随扩展不变，换入另一官方版本，验证上述关键链路和历史／草稿恢复。版本独立保存，失败时供新窗口选择旧组合；不能为回退而停止活跃 Agent。

通过这些条件后，再决定是否让原生宿主模式替代桌面复刻 UI。此次评估不删除既有成果：终端／Claude、项目和窗口管理、VS Code 服务／消息桥仍有复用价值；与原版发送链路重叠的自建 Codex UI 和宿主适配按明确边界逐步收敛。
