# 侧边聊天权限归属与菜单焦点验收

2026-10-16，Round 12。隔离前端为 **HTTP `http://10.30.0.24:48865/`**，绑定 `0.0.0.0`；全部业务 HTTP／WebSocket 使用测试夹具，只有该自有 Vite 的 HMR 连接保持真实。本批未向真实原生会话发送权限修改、消息或停止指令，未启用新的正式运行产物。

## 问题与修复

正常入口“附加文件 → 当前会话的更多操作 → 侧边聊天”创建独立 fork，但主会话仍保持选中。原 `AccessModePopover` 自行读取全局 `currentThreadId`，因此侧边菜单的只读、请求批准、计划模式和完全访问确认会修改主会话的本地待发送设置；侧边输入区其余控件却使用 fork id。

权限菜单现要求调用者显式传入 `threadId`：主输入区和展开输入区传当前主会话，侧边输入区传自身 id；显式 `null` 仍表示新会话默认设置，没有全局会话回退。移除菜单中的全局主输入聚焦请求，沿用菜单自身的焦点恢复。本次不改变原生权限能力判定、确认文案、确认生命周期或发送协议。

## 原版依据与边界

对照官方 `26.51007.21434` 的 `permissions-mode-dropdown-6fd05cb80d75.js`（SHA256 `47e487782904c09ea598ad153b4ed50cfeb06e2fc6ac4681ad7b58658971c3ce`）、Main／Core／Native 和 entry，共五个模块、32 个精确源码片段。Kt／tn／yn 与完全访问弹窗 Ht 均捕获明确的 conversationId／host；普通菜单关闭与 Escape 经 Core 的实际 DropdownMenu 关闭链恢复自己的 trigger，不调用 composer 聚焦。

Ht 的确认只执行捕获的回调后关闭，取消只关闭。其全局弹窗可在创建菜单卸载后仍持有原目标回调；这本身不是错误线程写入证据，也不能推导“确认后一定聚焦编辑器”。本地真实主输入区按 thread id 作为 React key，切换时卸载并取消未确认请求；没有证据支持原先怀疑的普通 A→B 确认串写。本次没有为该假设增加状态规则。

精确片段、偏移、源码哈希和反例记录位于忽略目录 `.dev-runtime/session-polish-round2-20261016/menus/permission-confirm-owner-audit/`。完整官方宿主中的最终物理焦点未实测；本批焦点结论限于源码链及本地真实组件／浏览器行为。
