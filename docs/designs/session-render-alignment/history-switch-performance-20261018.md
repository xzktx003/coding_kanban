# 历史切换、阅读位置与输入焦点验收（R30）

缓存的 1500 条密集 Markdown／代码历史原先仍使切换超过既有 500ms 门槛：WebKit 846.0ms、Chromium 742.0ms。最终同一原始用例分别为 **422.0ms、454.7ms**，完整后续断言也通过。两引擎各 23 项阅读、15 项输入／草稿及 4 项真实 Lexical 焦点控制通过。这是本次固定环境的测量，单次切换值不是延迟分布或独立因果实验。

## 实现范围

- `ThreadList` 使用按 thread 的选择订阅、稳定动作和 memo，避免选中状态使整列重新渲染；删除等待结束后重新核对当前选择，保留用户后选的会话。
- `CodexThread` 在跟随最新内容时保留小窗口，进入阅读时恢复缓冲。行原点从实际布局测量，前置区域和 padding 变化重新校正；首次 DOM 测量与已存在的部分可见行分开补偿。真实行高测量仍保留。
- `transcriptReadingPosition` 在贴底时保存最新位置意图，避免扫描 DOM／读取 scrollTop；脱离底部时保存真实可见行及小数偏移。微小向上输入、连续手势和返回底部意图分别处理，旧安静计时器不能覆盖新输入。
- Composer 和实际 Lexical 编辑器沿用原 owner key，将自动聚焦安排到下一帧；卸载取消，执行前核对当前 root、连接、布局和指针策略，并尊重后来选择的其他输入框。没有删除会话隔离 key，也没有接入新的 writer 权限。

开发 React 性能记录的候选改动已经撤回，`react-performance-retention.ts` 及其测试与 R29 基线一致。没有改变网关裁剪、历史恢复策略、正文回收预算、完成提示音或正式运行服务。

## 历史失败与夹具修正

所有失败输出均保留，后续通过不改写旧结果。早期 CPU profile 含负 timeDelta，不能按权重声称 CPU 时间；原生布局诊断也不作为净收益或最终性能通过依据。撤回的开发记录候选、行批次及中间布局候选均不在最终产品中。早期 `final-source/` 是中间候选；最终源码另存 `accepted-source-v2/`。

旧 Enter 入口未选中实际 owner，且状态入口已在 plus Portal；旧审批用例仍寻找不存在的“排队消息”。迁移测试入口后保留发送／输入法／审批参数断言。真实焦点测试最初将 WebKit 的既有 viewport 提示作为错误，且按命名导入读取 Vite 默认导出的 renderer；修正分类及同一挂载模块的导入后才计通过，页面错误仍要求为空。审批夹具补的是纯状态类型注解。Fastify 由测试进程显式使用已有服务端依赖；原非模态用例的源码哈希检查要求仓库根 CWD，首次错误执行目录没有产生交互验收。

扩大到 20 份旧控制的 strict 尝试仍是失败记录，涉及原有内存用例类型和导入问题。后续指定 13 份覆盖本轮改动及非模态控制，使用真实 Fastify 声明并保留 strict；不能概括为全部 E2E 类型检查通过。

**未闭合诊断：**早期 WebKit 草稿用例及一次诊断在刷新时出现同源 thread/list／events access-control `pageerror`，所有业务断言已经通过，但原批次仍失败。请求实现有 catch，不能据此认定未处理 Promise；普通 caught-fetch 以及有限／持续 SSE 对照后来都通过，也不足以证明根因或修复。修正 Enter 后首次完整 WebKit 15 项通过，原草稿源码及 `errors=[]` 未删除或过滤。保留此间歇风险，不把后续绿灯称为已修复。
