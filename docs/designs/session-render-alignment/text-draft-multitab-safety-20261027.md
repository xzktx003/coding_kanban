# 同浏览器多页文字草稿保护（2026-10-27）

本项属于会话模式完整对齐计划中的持久草稿和多端体验。草稿仍属于当前浏览器配置目录和服务来源，不同步到其他设备；项目关注集合和正文同步保持原有协议。

## 已复现问题

同一线程在两个页面打开。A 发送后等待回执，B 输入新草稿，A 的 `clearSubmitted` 仅比较自身内存 revision/text，再通过 persist 覆盖共享 localStorage，B 刷新后新文字消失。两个页面独立计数还可能产生相同 revision、相同文字，不能据此认定同一次编辑。

新聊天首次创建线程也有同类风险：A 等待创建返回时，B 修改同一个新聊天 owner；A 的 `move` 将来源无条件写为 null，删除 B 的草稿。Codex、Claude 和 ACP 共用此来源移动路径。

## 存储与状态规则

- 每次真实编辑增加 revision，并生成独立 writeId。提交捕获该身份，原有 owner 隔离和同页迟到回执保护保留。
- 新文字正文按 owner/writeId/本次保存随机 textRef 存放，entry 仅保存指针。正文先同步保存，指针随后发布；失败保留旧记录及内存输入。每个按键仍只写当前 owner，不序列化历史草稿集合。
- 保存成功后记录该正文已发布。回收仅针对已发布且不再是当前指针的正文；未发布的并发保存不会被误删。重试也使用新的正文地址。指针发布失败时删除本次未发布正文。
- 发送回执写入仅作用于捕获版本的清稿标记，并删除那个版本的正文，不覆盖 entry。即使另一页在检查和写标记之间编辑，新 writeId 也不会匹配旧回执。
- 新聊天移动先保存目标，再对原始来源版本写 remove 标记；另一页的新来源保留。读取时将 clear 投影为空草稿、remove 投影为 owner 缺失。目的地保存失败不清来源。
- 读取先冻结 entry 键列表，避免并发删除旧正文导致索引移动、静默漏读其他 owner。遇到旧正文已释放时，最多三次重读该 owner 的当前指针；持续不一致或损坏明确报告失败，不伪造空草稿。
- 旧全量 v1 记录保持只读备份，已有内联分片和 null 墓碑仍可读。既有无 writeId 草稿按完整文字/revision 匹配；新编辑采用唯一身份。原有迁移标记和部分保存重试基线保留。

同时编辑同一 owner 仍按最后发布的编辑覆盖，不提供文字合并。另一页新增输入不会主动抢走当前编辑焦点。发送清理只处理实际提交；没有自动发送、恢复 writer 或停止任务。

正常完成写入的旧正文和标记会回收。浏览器在同步多键保存的中途被硬终止时，可能留下未发布正文；本实现不把它当作已发布垃圾直接删除，因为另一个页面可能仍在写入。没有宣称跨键 localStorage 事务或崩溃中途的原子回收；正常配额失败路径会清理本次未发布正文。旧全量备份的既有正文保留不变。

## 红绿灯与证据

- 原实现的“另一页新文字”和“相同 revision/text 的另一编辑”两项实际失败，修复后通过。
- 独立审查复现首轮 move 丢新草稿，以及初版 marker 仍保留 1 MiB 已发送正文。现有回归分别核对来源恢复和清稿后存储量小于 1 KiB。
- 独立审查再复现动态索引枚举漏 owner、并发发布遗留旧正文，两条新增用例先红后绿；同时覆盖未发布正文不可回收。
- `sessionTextDraftStorage.test.ts` 与 `sessionDrafts.regression.test.ts` 当前共 27 项通过，包含读写间插入另一页编辑、两个不同版本的迟到回执、quota、legacy、move、缺失旧正文重读与正文回收。
- 浏览器新增 `tests/e2e/session-drafts-cross-page.spec.ts`，使用同一 browser context 的两页、真实公共编辑器和 localStorage，挂起 fixture 的发送回执；检查新文字/独立相同文字、刷新恢复、目标不变及恰好一次发送。所有业务请求由隔离 fixture 接收，不向真实 Agent 发送。

本轮局域网前端：HTTPS `https://10.30.0.24:8484`，端口 8484、监听 `0.0.0.0`。完整日志位于忽略目录 `.dev-runtime/session-multi-page-20261027/`；初次测试配置的模块加载错误和一次尚未到达业务步骤的页面加载失败均保留，不计通过。最终浏览器、输入性能和构建结果在完成后追加。


## 本批最终结果

文字草稿及实际消费者的 10 个单测文件共 65 项通过。最后新增“同一 writeId 重试到另一 textRef”的指针恢复回归，保留三次上限；独立 Storage 反例先失败，修正比较字段后通过。

浏览器本批 4/4 通过：两页延迟回执（新文字和独立同文编辑）、300 份各 5,000 字符旧草稿下真实 Lexical 输入、三页不同 owner 交错输入后刷新恢复。输入过程 87 次写入共 8,218 UTF-16 字节，单次最大 246 字节，原 8 KiB/64 KiB 阈值不变；观测到的最大键入至下一帧时间 52.1 ms 是该次合成输入样本，不是实体设备延迟保证。最终一行指针恢复比较修正后单测覆盖完整，两页常规流程与输入字节验收未被用来替代该竞态用例。

对应日志为 `text-unit-final.log`、`text-browser-v3.log`。初轮浏览器测试一例停在应用加载失败、未到达业务步骤，另一例通过；原失败日志保留。追加业务日志及同源证书初始化后，完整四例通过，不修改产品证书或放宽断言。前端验收没有向真实 Agent 发送消息，也未重启 Session 运行层。

最后完整 `pnpm check` 通过 shared、Session runtime、server、web 类型检查及生产构建，日志 `check-final.log`。首轮只因新增单测辅助类型未包含 writeId 失败，修正为共享 TextDraft 类型后重跑通过；原失败 `check.log` 保留。构建不等于替换活跃 Session 运行层。
