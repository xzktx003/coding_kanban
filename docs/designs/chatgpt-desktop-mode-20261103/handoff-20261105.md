## 4. 两条技术路径，不能混用结论

### A. 原版 Mac 前端＋自有 AppHost 桥（仓库主实现）

```text
四模式工作台 → ChatgptModeApp → 固定 Mac ASAR 资源
    → browser-entry / browser-bridge → HTTPS/WSS 网关
    → 私有 control broker → 容器内 Linux native
    → 自有唯一 view 的 AppHost MessagePort → Codex
```

这一条有完整真实两轮成功记录，核心问题是部分初始化突发触发 `BRIDGE_QUEUE_FULL / waiting_count`。预算、身份及未知回执保护均须保留。

### B. Linux 原版应用＋Xvfb＋VNC（最后新增的隔离备选）

```text
新冻结工作台的第四模式 → 同源 noVNC iframe → HTTPS/WSS 代理
    → 固定 loopback broker（私有 token）→ 私有 Unix VNC socket
    → 独立 VNC 口令认证 → Xvfb 内完整 Linux Electron 窗口
```

目的：让原版界面与 AppHost 都留在 native 本地，避开 A 路径的浏览器队列。这是为核心交付尝试的技术备选，**尚未证明真实收发、尚未成为最终产品架构**。

B 直接执行 Linux 包的 `/app/ChatGPT`，使用 Linux 自带前端，未替换为指定 Mac 资源。即使 B 核心通过，也不能据此宣布 Mac UI 1:1、自由分屏、公共输入、项目能力或共享任务完成。VNC 中文输入／剪贴板、视口适配、多个客户端控制和持久化也需要明确验证，不能靠现成页面存在推导。

## 8. Mac 桥队列问题：已有首因与不应重做的实验

真实只读页面在失败时：32 个 portPost 在途、232 个等待，合计原 264 槽；pending 总计 41（9 个普通调用＋32 个 portPost）；普通 waiting 为 0，传输 FIFO 帧／字节为 0，port 快照约 720711 字节，最近一次真实回执仅在 2 ms 前。不是简单的网络断开或队列字节超限。

等待消息包含 ROP `push / pull / release / resolve`。已定位的订阅源有账号 `accessInputs`、宿主 `recentThreads`、逐线程 `listState`、逐项 settings；样本不是全部消息的统计，不能据采样占比下结论。`recentThreads` 不能替代线程状态／审批订阅；延迟 settings 注册可能丢失 A→B→A 的中间更新。

| 已试方向 | 真实结论／停止原因 |
| --- | --- |
| portPost 32→56，保持总预算 | 真实新页面仍队列满，已撤回 |
| 入站 pacing／有界 delivery queue | 合成通过，真实账号仍失败，未集成 |
| 固定批次／滑动批次切换 | 真实成功与失败都出现，未证明解决根因 |
| WebSocket 小批合并 | 隔离耗时没有可观察改善，不上线 |
| 小消息编码优化 | 单条仅数微秒，不足以解释积压 |
| ACK 时同步提前释放槽位 | 真实浏览器任务之间本就清微任务，未证明吞吐收益，且须保护快照计费，未集成 |
| Node IPC 串行→少量并行 | 隔离 264 条总差不到 1 ms，不足以作为真实修复 |
| CPU 饱和假设 | 后续空闲采样无饱和／限流；未覆盖出错瞬间，既不能确认也不能排除历史瞬时压力 |
| 直接错峰／合并订阅 | 会漏事件或把积压转移到不计预算的隐藏队列，未集成 |

禁止仅扩大 64 pending、264 槽、8 MiB 等既有上限，禁止假 ACK、静默丢消息、无界外置队列和自动重发。继续此方向应提出新的可证伪假设及最小补丁，不再重复同一无收益基准。

## 10. 推荐的恢复开发顺序

1. 完成一个短的现状／验收合同核对，不重新讨论已确认产品范围。
2. 并行推进：前端修 HTTP/2＋接在线 broker；宿主处理原生输入和账号；UI 工程处理 CJK 字体与输入；测试工程修夹具并准备真实收发；独立 Reviewer 核对边界。Mac 桥工程只有新假设时继续，不阻塞其他可用路径。
3. 8506：先在私有配置中核对在线 broker／token 对应关系，再验证同源 HTTPS/WSS、未认证不可见／不可操作、认证后真实画面。只允许对这份尚未交付的独立候选按归属进行替换，不能重启 8505。
4. 由唯一操作者核对当前新聊天草稿并正确输入，单击发送一次。没有确定回执就先核对原生小元数据／记录，不再次点击。
5. 核心通过后，把实际候选改动迁入 `apps/web`、`apps/server`、`packages/*` 约定目录；隔离副本只是工作材料，不能成为唯一实现。逐项记录原包来源、产品功能和已知限制。
6. 给出可访问 LAN 地址、口令的私有读取方式、最短操作步骤和当前版本真实证据。继续补持久化／真实项目，然后分屏和一期其他范围。

## 13. 检查命令与证据纪律

按改动选择最小检查，不为汇报重复已有绿灯：

```bash
pnpm --filter @agent-orchestrator/chatgpt-desktop-host run check
node --test packages/chatgpt-desktop-host/test/browser-entry.test.mjs
pnpm --filter @agent-orchestrator/chatgpt-desktop-host test

```

上面不是要求每次全跑：提示改动选对应入口测试；共享接口要同时验证前后端；完整整合再选全包／`pnpm check`。缺少原包、Docker、账号夹具导致的 skip 不能当通过。具体的服务端、前端和原生专项见包 README 与各功能文档。

VNC 新副本的直接代理测试为：在其冻结 `stage` 中执行 `node --test apps/web/chatgpt-vnc-candidate.test.mjs`。先补真实缺失的 HTTP/2 情形，再改实现并转绿，随后立即进入真实 HTTPS 浏览器；不要用 HTTP/1.1 200 推导 HTTP/2 成功。

每次失败至少保留：准确版本／scope、第一次错误码、动作是否实际写出、一次操作次数、真实 native 生命周期、相关截图和有界日志。日志不得保存账号 token／口令或无关用户正文。不要为了收集更多诊断继续发送；已有未知结果先核对。

历史夹具问题已经包括随机欢迎文案假设、错误 DOM 标签、iframe 导航竞态、非原版模型按钮属性。夹具出现这类具体错误应修夹具并保留首因，不能当原版功能坏了，也不能靠放宽成“任意页面存在”让断言通过。
