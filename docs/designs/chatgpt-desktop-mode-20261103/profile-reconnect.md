# 第四模式的实例换代与手动重连

原版 iframe 内的连接错误按钮以前只刷新当前 URL。固定 profile 换代后，该 URL 仍包含旧的 profile/generation，用户无法通过按钮回到当前实例。

父页面只观察同源、当前 iframe 的原有错误提示，并且只接受提示内按钮的可信点击。点击后只读查询服务端固定 profile：身份相同则由用户手势刷新当前 iframe；身份改变则挂载新代次；不可达则显示现有重试入口。模式切换、页面显示、状态通知与脚本 click 不触发重连，也不发送或自动恢复会话。

每次可见性切换及文档更换都撤销旧的请求身份，迟到状态结果不能操作新窗口。工作树另增加原界面持续未就绪时的提示：20 秒后显示明确的重连操作，只有可信点击才查询 profile；状态读取失败保留现有 iframe 和草稿。这不证明或修复原生初始化耗时的根因。

早期仅增加重连处理时，隔离浏览器曾验证旧组件热更新后 iframe 和模拟草稿保留；该证据不覆盖此后新增提示的版本。对目前工作树版本的进一步 Vite 实测发现：从 8500 的旧组件直接热更新到当前版本会改变 hooks 签名并卸载 iframe；当前版本之间保持签名的更新则保留 iframe、文档和模拟草稿。另一份兼容旧签名的私有候选会破坏从当前工作树版本的热更新，因此没有覆盖当前源码。8500 是独立冻结部署，尚未接入本次提示；不同签名的版本须通过隔离发布与用户明确的页面切换处理，不能宣称两代之间的热更新安全。上述浏览器检查均未操作真实用户草稿。

新的 `vite.chatgpt-safe-candidate.config.mjs` 仅供独立新进程显式启用：它将旧的连续性插件替换为受保护实现，延迟可能卸载文档的 JS 更新并沿用显式刷新提示。隔离原版界面已验证慢提示、草稿保留和手动重连；旧页面不能追溯获得保护，8503 尚未接入。
