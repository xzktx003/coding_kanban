# Codex 窗口 409 与界面启动失败

## 现场证据

2026-10-26，局域网正式入口为 **HTTPS https://10.30.0.24:8484/?mode=codex，端口 8484**。只读检查发现：

- `.env` 仍指向 10 月 14 日 v17 宿主；`pnpm codex:status` 报告 `extension.cjs`、`control.cjs`、`appserver-send.cjs` 内容过期，HTTP 宿主及网关仍在线。
- 当前私有 broker 的 `/status` 显示多条历史 custom editor 位于同一原生编辑器组。恢复请求和显式焦点请求没有共用互斥通道，可能在 `vscode.openWith` 回执前互相切换全局活动编辑器；精确目标核对因而返回 409。确定性回归复现了这条失败路径，但没有将所有 409 都归为同一种原因。
- 18:58 的官方日志出现多个 `renderer_ready_timeout`，`receivedWebviewMessage=false`，约 30 秒超时；这对应官方“Codex could not start its user interface”错误。错误是渲染器握手失败，不能等同于登录失败或正常 onboarding。
- 同 UID 的 inotify 实例上限为 128，检查时观察到 125 个 inotify 文件描述符；官方日志持续报文件监听 `EMFILE`，额外开发服务也复现。句柄计数不等同于精确独立实例计数，资源压力与 renderer 超时的完整因果关系未单独证明。未结束其他进程或调整全机内核限制。

## 修复边界

`companion/control.cjs` 以宿主 API 对象为范围，将焦点操作至精确核对、以及新组创建与 open 提交串行化。新编辑器加载 Promise 不占用整个串行通道，维持独立打开能力；失败不会毒化后续队列。UUID、唯一编辑器、组与活动标签核对保留，不把 409 当成成功或自动重试发送。

原生观察器仅识别没有 React root 且标题、h1、p 完全匹配官方静态失败文档的情形。错误归属已有请求的列绑定，不能将另一会话正文或全局通知当成本窗错误。失败不计为 ready，并显示窗口启动超时。正常引导仍可操作；没有 composer 的审批或其他页面不再被误标为引导。没有改动官方 VSIX 或原生 iframe 父节点、MessagePort。
