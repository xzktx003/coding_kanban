首先完成下列可独立判定的定位工作，再继续阶段 1–3，不把后端保温与页面性能合并成一个绿色状态。

1. **补足恢复基线。** 隔离网关使用真实、完整的关注集合/窗口持久化实现，取代本轮最小目录/标签夹具；核对首次发送后的 thread UUID、实际 editor URI、local/session storage、原生 profile 状态和刷新后的精确选中目标。所有写入仅针对隔离测试会话。先排除夹具与持久化问题，再归因正式代码；目前 45 秒未恢复不能单独当作正式产品根因结论。
2. **定位官方启动关键路径。** 同步采集所有 renderer/OOPIF 的资源与执行时间、官方扩展的初始化 RPC 时长、私有实例发布和 thread hydration。先对照正常匹配 CLI 与常驻桥接，使用同一官方 profile、历史和浏览器缓存。现有 page-target 的字节数不代表全部 Webview/历史传输。只有确认由自有宿主或缓存契约造成的额外串行工作，才做修复；不修改官方 bundle、不改 feature flag、不伪造历史。
3. **独立草稿/profile 关卡。** 两标签和物理手机打开同一测试 thread，核对官方状态存储与独立草稿。若共享 profile 会互相覆盖，先验证自有 code-server profile 隔离的成本及真实状态同步；保持原生通道、iframe 父节点和 MessagePort。
4. **验证共享连接的生命周期语义。** 用可控真实任务、审批/提问和关闭/刷新制造竞态。校验旧连接不会改新轮次的设置，旧审批不会命中新请求，关闭发起端不结束后台任务，服务代次更换不能误报热就绪。连接 ID 隔离的单测不足以证明操作协调成立。
5. **重新执行性能关卡。** 在用户实际开发入口和诊断构建分别测同一目标；先得到正确 target 和真实 native 接受回执，再按原计划跑各场景 30 次、物理设备和自然内存长测。所有符合保温条件的样本仍必须 ≤ 2 秒，不以平均值、p95、截图或缓存文本代替通过。
