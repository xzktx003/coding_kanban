# Codex 会话浏览器内存预算与恢复

## 问题与修复

运行 Codex 时，隐藏的命令/文件输出 delta、未观察会话正文、交错的回复 delta、已完成工具结果和重复历史正文曾持续积累。仅使用虚拟列表只能减少 DOM，不能释放 store 中的正文。本次修复同时处理事件入口、数据归并、观察生命周期和容量回收。

- 共享 SSE 只建立一条连接；正文只留给关注、当前、仍展示的会话及其已知子 Agent。退出观察范围释放正文和分页，取消只读请求并拒绝迟到回填。
- 按 thread/turn/item 和 reasoning part 合并文本 delta，交错事件也不会阻止合并；最终快照替换同一消息的流式副本。隐藏的原始输出不进入显示历史，最终工具结果按下述预算保留。
- 完成轮次和线程元数据去掉重复 items 正文；关闭后恢复基线、命令状态/耗时和列表行展开状态同步清理。原生任务、草稿、待审批请求与飞书通知不依赖这些显示缓存。

## 容量与自动释放

`sessionMemoryGovernor.ts` 挂载在会话工作台，事件变化最多等待 250 ms 检查；即使没有新消息，也每 5 秒检查一次，页面隐藏时再检查。估算器计算字符串和对象占用，不为估算再生成一份 JSON；这些数值是显示数据预算，不是浏览器进程 RSS 上限。

| 检查条件 | 回收目标 |
| --- | --- |
| 单会话显示正文超过 8 MiB，或事件超过 3000 条 | 向 4 MiB / 1500 条收缩 |
| 所有会话显示正文合计超过 32 MiB | 分配更小的会话预算，向合计不超过 16 MiB 的目标收缩 |
| 浏览器提供堆指标，已用 JS 堆超过 256 MiB 或堆上限的 70%（取较小值） | 加强回收，单会话预算最多 4 MiB，目标最多 2 MiB；事件 1500 → 750 |

浏览器不支持堆指标时，仍执行正文预算和定时回收。优先释放旧的完整轮次；单个长轮次内也释放旧的已完成工具组，最多保留 256 个完成工具组，并进一步按字节预算缩减。大型工具文本显示为最多 64 KiB 字符预览，带明确截断标记；单条助手回复、计划、推理文本段和轮次完整 diff 最多保留 256 KiB 的首尾预览，中间内容有明确标记。用户输入、最新回复、正在运行的工具和协作状态优先保留，不盲目清理正在加载的历史页；正常阅读时保护当前读入的旧页，堆压力下允许释放其浏览器副本。

边界：消息和单次任务 diff 正文在进入浏览器会话缓存前有上述单条上限，但多个受保护的运行状态合计仍可能超过会话预算。截断只作用于 Kanban 的显示缓存，完整 Codex 原生历史不修改，可通过原生历史读取完整内容。图片、终端、保活的 VS Code iframe、浏览器原生资源各有自己的生命周期。应用释放引用后由浏览器 GC 回收，不调用生产环境强制 GC，也不能承诺 RSS 立刻下降或所有资源总量绝不增长。

## 释放后的只读恢复

旧轮次释放后保留浏览器本地恢复游标，点击加载更早记录时先按 `thread/turns/list` summary 找到保留边界，再读取最多 10 个轮次的 full 页面。单个长任务的旧工具结果使用 `thread/items/list` 每页 20 条恢复；部分工具页面与现有消息合并，不把正在运行的轮次改成 completed。恢复页排在同轮用户输入之后、保留消息之前。

本地游标不会作为原生 cursor 发送。边界消失、重复原生游标或超出扫描限制均显式失败，不猜测历史、不 resume、不获取写入权。实时漏事件补查最多 5 页或约 8 MiB，其他内容留给显式分页；保留磁盘历史、输入草稿、审批和运行状态。兼容性说明：单轮工具分页需要运行层支持原生 `thread/items/list`，不支持时报告读取错误，不以全量历史读取替代。

## 2026-10-10 真实工具生命周期与缓存峰值补修

用户在浏览器任务管理器中仍观察到 Kanban 标签页内存过高。上一轮测试只注入 completed 工具、主动调用回收器并在测量前强制 GC，不能覆盖真实运行的 started(inProgress) → completed(completed)、自动回收和持续缓存写入。因此原先测试数值仅代表当时 fixture 的回收后状态。

本轮明确复现两条遗漏路径：

1. 回收分组以逻辑 OR 累积 `inProgress`，开始时为运行中的工具在完成后仍被永久保护；500 对真实开始/完成事件原来保留约 63 MB。改为采用后续状态覆盖，并继续保留实际运行中的工具。
2. 容量回收每删除一个工具或轮次就 filter 整个数组并重新估算，产生平方级临时分配；改为先计算事件占用，再扣减字节和数量，最后一次过滤。旧观察预算也复用对象估算器，停止反复 JSON 序列化整个正文。

历史缓存容量检查现在先裁剪数据，再作一次有界 JSON/UTF-8 序列化；每个缓存 key 只允许一个写入过程和一份最新待写快照，替换旧待写内容并确保等待者正常完成，不能无界堆积写入任务。缓存估算保持对象不可变，防止裁剪后复用旧占用估算。大型工具快照在事件入库前立即裁剪为带标记的 64 KiB 显示预览，不等待后续定时回收，避免突发正文先进入所有订阅与缓存链路。原始通知对象不被修改，原生磁盘历史继续保留。写入队列接收的也是预裁剪后的记录，不持有原始大正文。

真实页面检查中，`performance.memory` 的值可能在 CDP 已观测到堆增长时仍保持不变。因此新增无正文引用的流量计数：5 秒内进入显示链路的通知估算达到 16 MiB，也触发加强回收；安静 5 秒后退出该压力信号。该机制不依赖 Chromium 堆 API，隐藏或未观察正文仍在入口过滤。

浏览器新增真实 started/completed 连续压力测试，使用正常挂载的自动回收和设备缓存链路，测试内不调用回收器、不强制 GC。该测试不能替代用户设备长期运行记录，但比上一轮主动回收的 fixture 更接近实际事件生命周期。

本轮最终浏览器复测：10 个用例通过，包含移动/桌面打开定位、回滚、隐藏/无关输出、可恢复的旧历史，以及真实运行轮次 2400 对开始/完成通知（累计约 240 MB 原始输出）。最后一项不强制 GC、不调用回收器，正常缓存写入开启；JS 堆峰值 173,629,120 字节（约 166 MiB），浏览器自然回收至 56,286,136 字节（约 54 MiB），最终 113,425,120 字节。显示正文各批均低于 8 MiB，当前轮次仍为 inProgress。数值为隔离 fixture 的 JS 堆，不等于用户标签页进程总内存，也不据此保证任意单条巨大回复或所有原生资源的绝对上限。

最终代码快照检查通过：`pnpm check`；会话单测 216 文件 / 825 用例，终端 530，后端 696 通过 / 1 跳过，脚本 95。缓存限容、写入合并、失效后的排队写入及不依赖堆 API 的流量压力均有回归；相关 6 文件 53 用例复核与独立 TypeScript 检查通过。仅保留现有构建 chunk 提示，无新增依赖，也未重启原生 Agent。

此前提到的 `frameTextDeltaQueue` 只能确认属于终端/native output 路径。未找到 conversation agent 文本通过该帧队列批处理的直接证据；官方 conversation reducer 仍直接把文本片段追加到对应 item。因此不声称官方聊天采用 rAF 文本队列，也未找到其全局 Markdown AST 缓存的明确证据。

本轮落地的是证据明确、范围受控的命令快照归一：开始时显示运行状态，完成时同位置替换为最终快照；读取历史按原生状态生成一份快照，不把仍在执行的命令伪造为完成。用户输入、推理、审批和子 Agent 保留各自事件语义。最终助手消息仍分隔前后的命令组，避免去掉开始副本后把不相邻命令合成一组。

## 2026-10-10 类似对话产品的流式渲染对照

检查 GitHub 上 Open WebUI 的公开实现：[Messages.svelte](https://github.com/open-webui/open-webui/blob/main/src/lib/components/chat/Messages.svelte) 对流式消息的列表重建使用 `requestAnimationFrame` 合并到每帧一次，结构切换立即重建；[Markdown.svelte](https://github.com/open-webui/open-webui/blob/main/src/lib/components/chat/Messages/Markdown.svelte) 对未完成消息每帧最多重新切词一次，并在组件卸载时取消待执行帧。它默认分批显示最近 8 条消息，向上翻页时再增加 8 条。[Message.svelte](https://github.com/open-webui/open-webui/blob/main/src/lib/components/chat/Messages/Message.svelte) 还用 `content-visibility: auto` 跳过屏幕外消息的布局和绘制，明确注明 WebKit 的兼容问题并在该环境停用。

Kanban 原先虽然有虚拟列表和原生历史分页，流式文本每个通知仍会触发 `buildThreadRows` 扫描整段事件；随后把最后一条完整消息 `JSON.stringify`，即使只是同一消息多一个 token；可见助手消息的 `Streamdown` 也随每次更新重建。长回复令这些全量操作反复处理不断变长的字符串，造成高频临时分配和解析，符合用户报告的“Codex 工作中内存快速上涨”时机。这是本轮定位到的前端放大路径，不把它混同为所有机器上的唯一原因。

本轮按上述模式修复：流式文本、计划和推理 delta 先按 thread/turn/item/part 合并，最多每帧向 Zustand 提交一次；同一线程的非 delta 通知会先冲刷待处理 delta，避免完成事件越过文本，卸载时也会冲刷队列。会话行推导、送达回声扫描和 Markdown 子树因此最多每帧更新一次。新消息提示只比较末行稳定 key，不再序列化正文。线程状态、审批和其他非 delta Codex 通知仍立即进入 store，流式正文增加最多一帧的合并延迟。历史仍沿用原生分页和既有内存预算。

另一个重要对照是 OpenAI Codex 自身的公开 issue [#39231](https://github.com/openai/codex/issues/39231)：报告描述大文件 diff tracker 长期持有原文、每次变更重建/克隆完整 diff 并写入日志，最终 RSS 达数十 GB。它说明 Codex 任务期间的内存增长也可能来自运行时/工具和文件 diff，而不只来自聊天 UI；Kanban 的前端修复不能限制这些进程的 RSS。检查日为 2026-10-10；上游 issue 状态和实现会变化，引用用于说明已报告的问题类型，不推断所有用户或插件都会复现。

同日补充入口优化：单个 transport 通知仍会经过解析，但连续流式 delta 不再逐条复制 Zustand 事件数组并触发 store 订阅；hook 在帧队列中按消息/part 合并后调用一次批量 store action。所有同线程结构事件先同步刷新队列，任务结束时的最终快照不会越过尾部文本。

## 2026-10-10 单条长回复与 diff 限容

之前自动预算会保护最新助手回复，因此一条超长回答或轮次 diff 能越过单会话预算；流式 delta 合并后也没有重新限容。现对单条助手回复、计划、推理文本段和完整轮次 diff 设置 256 KiB 字符上限，保留首部与最新尾部，并插入“中间内容因会话内存限制已省略”标记。流式内容每次合并后再次限容，不会随任务长度持续增长。大型工具输出和文件变更字段仍按各自 64 KiB 上限保留显示预览。

这些上限作用于 Kanban 会话显示缓存，不改变 Codex 原生历史文件；需要完整内容时仍可通过原生历史读取。回归用例先验证 300 KiB 最终回复、计划、推理、diff 和持续累积 delta 会突破边界，再验证每项均有界且保留首尾；帧缓冲另有集成用例。全会话测试 217 个文件 / 834 个用例、全局类型检查和生产构建通过。未在用户的真实长任务上重新采集 heap snapshot，因此这里只能确认前端缓存上限与构建，不据此声称浏览器标签页总内存具有固定上限。

## 2026-10-10 流式回复仍造成堆增长

上一轮每帧合并 delta 仍把不断增长的消息写回整份 `events[threadId]`。`CodexTranscript` 因此每帧重新运行 `buildThreadRows`；可见的 `Streamdown` 也会对增长中的 Markdown 全文重新分块，并通过 React transition 更新块状态。旧测试只验证直接 store 注入、静态长历史或工具生命周期，没有测到“真实通知处理器 → 可见流式回复 → Markdown”这条路径，所以只能证明事件限容，不能证明页面分配稳定。

现将正在生成的助手正文放到 `streamingAgentMessages`，正文保持 256 KiB 上限，并作为独立的末尾消息显示为保留换行的纯文本。增量不再复制历史事件数组，不再重建整段 thread row 模型，也不在每个 token/frame 重跑 `Streamdown`。收到 `item/completed` 后，在同一次 store 更新中清除临时正文并加入有界最终快照，Markdown 只解析最终消息一次。若 turn/error 终止时缺少最终快照，则把有界部分回复保留为一条 delta 历史，避免丢失用户已看到的输出；运行时重启或线程离开观察范围会清掉临时正文。

继续检查后发现，256 KiB 上限虽然限制了保留量，旧累积器仍在每次增量时拼接已生成全文；超限后还会反复复制整份首尾预览，产生与任务时长成正比的短命字符串分配。这会让堆/RSS 继续上行，尽管状态本身有上限。现改成 8 KiB 稳定文本段：预算内只追加当前小段；超出预算后首部段保持不变，只滚动维护尾部段。帧缓冲也只物化一次有界预览再交给 store，活动渲染不拼整段字符串。结束时需要保留中断回复才一次性合并段落。

回归覆盖了 300 KiB 流式正文不进入历史数组、首段在尾部更新时保持引用、最终快照替换临时副本、活动期间绕过 Markdown parser，以及真实浏览器事件桥接。Chromium 页面接收 400 条、总计约 3.2 MiB 的 Codex delta；CDP 在五个批次边界采样的 V8 堆为：基线 30,588,972 字节、峰值 36,540,388 字节、强制 GC 后 32,983,980 字节。该隔离用例显示输入正文没有等量留存在 JS 堆里，但采样不等同连续峰值，也不测浏览器任务管理器的进程 RSS，用户真实长任务还需复测。会话单测 218 文件 / 845 项、`pnpm check` 与生产构建通过。流式回复完成前 Markdown 标记会暂时以纯文本显示，完成后恢复正常格式。

## 2026-10-10 截断预览仍持有原始大字符串：物理留存回归

此次定位到前几轮字符数预算遗漏的实际留存问题：V8 的 `SlicedString` 可以通过 parent 引用保留原始字符串，`ConsString` 拼接省略标记也不保证断开该引用。因此 `slice(0, 64 * 1024)` 得到的工具预览，逻辑上只有 64 Ki 字符，实际却可能牵住整份 4 MiB 输出；按 `length * 2` 计算的预算看不到 backing store。机制见 [V8 官方字符串说明](https://chromium.googlesource.com/v8/v8.git/+/refs/heads/main/docs/objects/strings.md)。这能够解释工具工作负载中“限容后仍涨”的一种明确原因，不代表已经取得用户现场的 heap snapshot。

浏览器先红后绿：通过项目实际 `compactCodexEventPayload` 保留 16 份各 4 MiB 的工具输出预览，总字符数 1,048,576。修复前 Chromium 强制 GC 后堆增量为 **67,115,496 字节**；修复后同用例为 **1,047,600 字节**。此前只断言事件数量和字符串长度的测试无法发现这种引用保留。

修复在截断结果和流式段落的持久化边界调用 `copyTranscriptText`，只复制有界预览，生成不引用原始大文本的字符串；保持已有预算、首尾预览和省略标记，不增加新的缓存/定时器/依赖。`split("").join("")` 保留 UTF-16 代码单元，包括单独代理项；不使用会替换非法代理项的 UTF-8 编解码。仅依靠 `slice`、`substring` 或拼前缀再切片不能代替这一步。复制有少量有界临时分配成本，收益是原始大输出可被 GC；普通未截断历史消息保持原引用。

新增浏览器回归覆盖工具输出、MCP 结果、最终回复和流式首尾预览四条路径。最终回复的中文省略标记会使字符串使用双字节表示，因此物理预算按字符数的两倍加 4 MiB 页面余量判断，而不是把 4 Mi 字符错误地等同于 4 MiB。另通过真实通知桥接发送助手 delta，再混合 24 次命令 started/completed、推理和计划更新，命令原始输出共 96 MiB；3 个批次中不强制 GC，批次堆采样为 105,515,756 / 98,265,264 / 122,222,768 字节，最终诊断 GC 后由基线 32,401,072 到 34,988,060 字节（增加约 2.47 MiB）。这些是 V8 JS 堆指标，不是浏览器进程 RSS，也不是长期任务的连续峰值。应用没有调用强制 GC。

## 2026-10-10 工具调用退出聊天显示缓存

用户明确不需要在会话对话窗口看到工具调用，因此策略从“折叠并保留有界预览”改为“聊天不展示、不持有工具正文”。`codexTranscriptVisibility.ts` 统一识别命令执行、文件变更、MCP/dynamic 工具、搜索/图像工具和子 Agent 调用，以及输出 delta、进度、终端交互、patch、轮次 diff 与自动审批复核状态。实际审批请求走独立请求存储，不受此聊天过滤影响。

过滤在实时 `addEvent` 前、历史 item 转换、最终历史合并入库、缓存读写与旧缓存清理处执行；`turn/started`、`turn/completed` 和 `thread/started` 内嵌工具项也被剥离。显示层对旧输入再次过滤，避免出现命令组和 diff 汇总。实时处理器先处理独立子 Agent 观察和请求生命周期；原生历史恢复在丢弃工具正文前同样提取子 Agent 父子关系，防止离线期间创建的子 Agent 消失。纯工具事件不会触发聊天 store 更新，也不再复制聊天命令状态/耗时映射。最终消息、结构化提问、计划、warning/error 和 turn 状态保留。

此变更不修改原生 CLI 历史、工具实际执行和终端模式完整记录。网络上收到的工具 JSON 仍需要短暂解析，因此只能承诺不在聊天数据和 DOM 中累积，不能宣称网络解析的瞬时开销为零。旧页面已经持有的引用需要通过重新加载或现有清理路径释放。

浏览器真实通知桥回归仍输入 24 次 started/completed 命令，共 96 MiB 输出，并混合推理/计划；现在断言 retained transcript 中命令数为 **0** 且页面不存在命令行。一次采样基线 32,136,092 字节、三批采样 55,678,508 / 81,942,024 / 105,579,952 字节、诊断 GC 后 32,735,648 字节（增加约 0.57 MiB）。原先有界预览实现的同类负载增量约 2.47 MiB，仅作隔离测试参考，非用户现场 RSS 对比。直接压缩 helper 的四类物理留存回归继续保留，防止以后其他入口复用时重新引入字符串父引用问题。

侧边聊天 fork 的元数据也复用轻量线程快照，只保留 turn 状态而清空 items，避免在 `threads[].turns[].items` 中另存整份工具/回复正文。此路径新增先红后绿回归。验证：主会话套件 219 文件 / 857 项通过，补充侧边聊天后相关 3 文件 / 36 项通过；9 项浏览器回归通过，类型检查和生产构建通过。


## 2026-10-10 浏览器接收前裁剪与空闲同步去重

本轮重新用连接真实后端的 Chromium 页面采样，未发送任务、未打开右侧面板。旧代码 125 秒内 renderer RSS 从约 299 MiB 到 457 MiB；90 秒时自然 GC 曾将 JS 堆约 74 MiB 降到 37 MiB、监听器从 2857 降到 924。因此监听器数量的短期上升不能直接作为泄漏证据，也不能用最终 store 条数证明进程内存受控。

已确认的额外分配路径：

- 项目与关注标签每 2 秒接受快照，即使字段未变化仍发布新的 Zustand 根状态。完整订阅这些 store 的 Markdown、卡片和导航会重复渲染。相同快照现在返回原状态，不通知订阅者；操作确认、错误恢复和真实远程修改仍正常发布。
- 历史 watchdog 原本在活动轮次静默 5 秒、空闲 30 秒后重新读取完整最近历史。静默长工具不是丢消息证据；完整历史先进入浏览器再过滤，会重复分配隐藏工具输出。历史恢复改由连接缺口、发送回执缺失、完成状态、手动核对和页面恢复触发。
- SSE 与只读历史原本都在浏览器解析后才裁剪。浏览器现在显式请求 `view=chat`，Node 网关在送出前压缩工具正文；原生历史与后端内部消费者继续保留原协议。SSE 的序号连续性、审批/提问、轮次生命周期及子 Agent 结构信息必须保留；不能直接丢帧造成补偿风暴。

新增验证覆盖相同快照不发布更新、静默活动/空闲不轮询完整历史、完成时恢复，以及真实 HTTP/EventSource 传输压力。原有直接调用假 EventSource 回调的测试只覆盖前端消费，不能替代传输层验证。测试中的诊断 GC 不进入产品；浏览器自行决定何时回收已不可达对象。

浏览器专用 SSE 单帧限制为 16 MiB。超限或超大损坏帧由网关发送命名事件 `session-projection-error`，终止该读取流并释放上游；前端暂停实时接收、显示原因，不循环回放同一大帧。后台 Agent 不受影响。用户显式重试时从当前事件位置重新连接，并通过只读历史恢复可见消息。正常裁剪帧保留原序号，不制造缺口；审批请求不因聊天过滤被静默丢弃。状态列表还利用 `updatedAt` 在外部空闲会话保存新记录后触发补读，活动工具进度的时间戳变化不会重新触发完整历史轮询。

验证结果（稳定代码、真实后端、未发起 Codex 任务）：125 秒内 Chromium renderer RSS 起点 266.5 MiB、终点 253.8 MiB，采样范围 230.4–288.7 MiB；未强制 GC，监听器从 1001 到 975，最近历史请求 3 次（旧采样为 16 次），页面无 JS 异常。与前述旧版本采样属于同一后端的先后观测，期间后端会话状态会变化，不能视为严格控制全部变量的基准，也不能据此保证所有长任务无泄漏。构建期间的开发热更新采样不作为稳定性证据。

真实 HTTP→Node gateway→Chromium 原生 EventSource 压测：24 个 4 MiB 工具输出相关帧，加审批与最终助手回复，原始流量 100,669,814 字节；浏览器仅收到 4,964 个 SSE 数据字符，最大单帧 216 字符，26 个序号连续。诊断 GC 后堆增量 35,964 字节。另有 17 MiB 单帧测试确认只收到一次命名错误事件，不收到巨量普通消息。这里的留存堆指标不等同于浏览器 RSS；字节削减直接验证隐藏正文没有通过网络进入标签页。
