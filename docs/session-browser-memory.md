# Codex 会话浏览器内存预算与恢复

## 问题与修复

运行 Codex 时，隐藏的命令/文件输出 delta、未观察会话正文、交错的回复 delta、已完成工具结果和重复历史正文曾持续积累。仅使用虚拟列表只能减少 DOM，不能释放 store 中的正文。本次修复同时处理事件入口、数据归并、观察生命周期和容量回收。

- 共享 SSE 只建立一条连接；正文只留给关注、当前、仍展示的会话及其已知子 Agent。退出观察范围释放正文和分页，取消只读请求并拒绝迟到回填。
- 按 thread/turn/item 和 reasoning part 合并文本 delta，交错事件也不会阻止合并；最终快照替换同一消息的流式副本。隐藏的原始输出不进入显示历史，最终工具结果按下述预算保留。
- 完成轮次和线程元数据去掉重复 items 正文；关闭后恢复基线、命令状态/耗时和列表行展开状态同步清理。原生任务、草稿、待审批请求与飞书通知不依赖这些显示缓存。

## 容量与自动释放

`sessionMemoryGovernor.ts` 挂载在会话工作台，事件变化最多等待 250 ms 检查；即使没有新消息，也每 5 秒检查一次，页面隐藏时再检查。估算器计算字符串和对象占用，不为估算再生成一份 JSON；这些数值是显示数据预算，不是浏览器进程 RSS 上限。

| 检查条件 | 回收目标 |
| --- | --- |
| 单会话显示正文超过 8 MiB，或事件超过 3000 条 | 向 4 MiB / 1500 条收缩 |
| 所有会话显示正文合计超过 32 MiB | 分配更小的会话预算，向合计不超过 16 MiB 的目标收缩 |
| 浏览器提供堆指标，已用 JS 堆超过 256 MiB 或堆上限的 70%（取较小值） | 加强回收，单会话预算最多 4 MiB，目标最多 2 MiB；事件 1500 → 750 |

浏览器不支持堆指标时，仍执行正文预算和定时回收。优先释放旧的完整轮次；单个长轮次内也释放旧的已完成工具组，最多保留 256 个完成工具组，并进一步按字节预算缩减。大型工具文本显示为最多 64 KiB 字符预览，带明确截断标记。用户输入、最新回复、正在运行的工具和协作状态优先保留，不盲目清理正在加载的历史页；正常阅读时保护当前读入的旧页，堆压力下允许释放其浏览器副本。

边界：正文和最新回复可能单条超过预算，运行中的大量必要状态也可能超过预算；预算是安全回收目标。图片、终端、保活的 VS Code iframe、浏览器原生资源各有自己的生命周期。应用释放引用后由浏览器 GC 回收，不调用生产环境强制 GC，也不能承诺 RSS 立刻下降或所有资源总量绝不增长。

## 释放后的只读恢复

旧轮次释放后保留浏览器本地恢复游标，点击加载更早记录时先按 `thread/turns/list` summary 找到保留边界，再读取最多 10 个轮次的 full 页面。单个长任务的旧工具结果使用 `thread/items/list` 每页 20 条恢复；部分工具页面与现有消息合并，不把正在运行的轮次改成 completed。恢复页排在同轮用户输入之后、保留消息之前。

本地游标不会作为原生 cursor 发送。边界消失、重复原生游标或超出扫描限制均显式失败，不猜测历史、不 resume、不获取写入权。实时漏事件补查最多 5 页或约 8 MiB，其他内容留给显式分页；保留磁盘历史、输入草稿、审批和运行状态。兼容性说明：单轮工具分页需要运行层支持原生 `thread/items/list`，不支持时报告读取错误，不以全量历史读取替代。

## 2026-10-10 真实工具生命周期与缓存峰值补修

用户在浏览器任务管理器中仍观察到 Kanban 标签页内存过高。上一轮测试只注入 completed 工具、主动调用回收器并在测量前强制 GC，不能覆盖真实运行的 started(inProgress) → completed(completed)、自动回收和持续缓存写入。因此原先测试数值仅代表当时 fixture 的回收后状态。

本轮明确复现两条遗漏路径：

1. 回收分组以逻辑 OR 累积 `inProgress`，开始时为运行中的工具在完成后仍被永久保护；500 对真实开始/完成事件原来保留约 63 MB。改为采用后续状态覆盖，并继续保留实际运行中的工具。
2. 容量回收每删除一个工具或轮次就 filter 整个数组并重新估算，产生平方级临时分配；改为先计算事件占用，再扣减字节和数量，最后一次过滤。旧观察预算也复用对象估算器，停止反复 JSON 序列化整个正文。

历史缓存容量检查现在先裁剪数据，再作一次有界 JSON/UTF-8 序列化；每个缓存 key 只允许一个写入过程和一份最新待写快照，替换旧待写内容并确保等待者正常完成，不能无界堆积写入任务。缓存估算保持对象不可变，防止裁剪后复用旧占用估算。大型工具快照在事件入库前立即裁剪为带标记的 64 KiB 显示预览，不等待后续定时回收，避免突发正文先进入所有订阅与缓存链路。原始通知对象不被修改，原生磁盘历史继续保留。写入队列接收的也是预裁剪后的记录，不持有原始大正文。

真实页面检查中，`performance.memory` 的值可能在 CDP 已观测到堆增长时仍保持不变。因此新增无正文引用的流量计数：5 秒内进入显示链路的通知估算达到 16 MiB，也触发加强回收；安静 5 秒后退出该压力信号。该机制不依赖 Chromium 堆 API，隐藏或未观察正文仍在入口过滤。

浏览器新增真实 started/completed 连续压力测试，使用正常挂载的自动回收和设备缓存链路，测试内不调用回收器、不强制 GC。该测试不能替代用户设备长期运行记录，但比上一轮主动回收的 fixture 更接近实际事件生命周期。

本轮最终浏览器复测：10 个用例通过，包含移动/桌面打开定位、回滚、隐藏/无关输出、可恢复的旧历史，以及真实运行轮次 2400 对开始/完成通知（累计约 240 MB 原始输出）。最后一项不强制 GC、不调用回收器，正常缓存写入开启；JS 堆峰值 173,629,120 字节（约 166 MiB），浏览器自然回收至 56,286,136 字节（约 54 MiB），最终 113,425,120 字节。显示正文各批均低于 8 MiB，当前轮次仍为 inProgress。数值为隔离 fixture 的 JS 堆，不等于用户标签页进程总内存，也不据此保证任意单条巨大回复或所有原生资源的绝对上限。

最终代码快照检查通过：`pnpm check`；会话单测 216 文件 / 825 用例，终端 530，后端 696 通过 / 1 跳过，脚本 95。缓存限容、写入合并、失效后的排队写入及不依赖堆 API 的流量压力均有回归；相关 6 文件 53 用例复核与独立 TypeScript 检查通过。仅保留现有构建 chunk 提示，无新增依赖，也未重启原生 Agent。
