# 新网关与旧会话服务的发送兼容（2026-10-31）

## 现场故障

更新至 `42d85883` 后，网关和页面已包含 `118748b8` 的官方共享 daemon 协议，但仍复用既有 legacy 会话进程。健康检查成功不代表具备新版协议。

现场只读检查确认：`/api/session/health` 返回 200 和原运行 instance；`/api/session/lifecycle/context` 返回 500（上游缺少 operation-context，空错误体又被 JSON 解析遮蔽）；`/api/session/followups` 返回 409。发送服务先读取 lifecycle context，失败时尚未 POST 消息，草稿因此保留。网关默认选择官方队列适配器又导致旧会话队列不可读。

前端服务测试模拟 context 总是成功；网关队列测试同样模拟新版 operation-context 和 queue，没有覆盖新网关连接仍存活旧服务的组合。

## 兼容边界

兼容选择必须来自实际健康描述，而不是任意接口失败。已识别的旧健康格式与新版 `runtime: typescript`、`codexBackend: shared-daemon` 分开处理。新版接口的 404、500、超时、无效上下文或账号变更继续拒绝，不得退回 legacy 写入。

旧服务保留既有 `CodexFollowups` 调度与 ownership 检查，不伪造官方 queue、daemon 身份或账号授权。兼容发送上下文只表示网关观察到的旧运行实例，须明确标记，并在发送前复核；它不等价于原生 guarded RPC 的账号/连接版本检查或跨进程原子性。管理、原生已读、共享队列等新版能力不能据此假装可用。

已有草稿、未知送达结果和持久队列保持。不能为恢复发送重发未知请求、自动投递更新前残留队列、停止 Agent、自动刷新页面或替换仍存活的会话运行服务。运行层真正切换仍须安排安全窗口。

## 验证要求

新增回归须覆盖实际 HTTP 预检→队列读取→显式提交→一次 native start 的 legacy 组合；还须覆盖新版故障不降级、运行实例变化拒绝、未知回执不重发，以及旧持久队列不在初始化时自动执行。夹具只能驱动自有假运行服务，不向正式 Agent 发送测试内容。

正式只读复验使用现有 LAN 页面 **HTTPS `https://10.30.0.28:8484`，端口 8484**，网关内部为 loopback HTTP；地址来自当前配置，不写入源码常量。修复前原 Session 运行 PID 为 `3349013`。测试和最终结果另附本轮记录。
