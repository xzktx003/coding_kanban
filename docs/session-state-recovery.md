# Codex 实时状态核对与恢复

## 已确认的问题

现场消息已经取得原生 turnId，原生历史也有相同 clientId 的用户消息、回复与工具调用，网页却长期停在“已接收，等待消息同步”。运行层、网关和局域网 HTTPS 事件入口的只读抽样一致；没有取得出问题浏览器当时的网络记录，不能把具体断点归因于某一层。

代码复现确认：事件跳号或订阅处理失败没有触发核对；发送占位的历史补偿依赖已收到结束事件；已接收轮次在没有下一条排队消息时不会主动核对完成。这些缺口均可能让正文、转圈、计时和队列占用长期不一致。

## 恢复规则

- 会话首次连接成功后，历史、状态和辅助同步的生命周期跟随工作台，不跟随单次 `/health` 探测结果。探测失败仍保留已有输入与只读恢复工作，实际请求按各自的超时、退避和页面可见性规则执行；只有工作台卸载才清理这些同步器。
- SSE 重连快照携带服务端当前游标。若快照游标小于本地已处理序号，判定运行实例序号已重置，复用实例恢复流程清理旧请求身份，并从新游标重新订阅。普通重复帧仍去重，同序号快照仍正常处理。

- 共享事件流检测跳号、非法帧和处理失败，合并恢复请求；仍处理其他健康订阅者。使用既有游标重新连接并补齐状态，恢复性重连限频，不重放已确认的用户操作。重复的普通事件继续去重，同序号待交互快照照常处理。
- `followedSessionHistorySync` 统一恢复关注会话及本机暂留会话，使用 `thread/read`。已接收但缺少原生消息时约 3–4 秒开始核对；运行中/有接收轮次但缺乏进展时约 10 秒核对。最多 2 个历史查询并发，失败按 5/10/20/30 秒退避；选择当前会话优先，隐藏页面停止周期巡检，返回前台重新核对。
- `followedSessionStatusSync` 在可见页面每 30 秒补一次状态快照，并响应事件异常。历史与快照仍遵循现有迟到回执保护，不改变选中会话、草稿、模型或布局。
- 历史核对补回同一已观察轮次的完成时更新未读提醒。冷加载旧历史和历史回退不会补发旧的未读提醒，也不补播声音。滚动仍交由既有“阅读中不跟随、回到底部才跟随”的机制处理。
- 同步失败显示自动重试状态，“重新同步”只触发只读核对。已送达消息保持原 ID，核对、重连均不调用发送、resume、interrupt 或自动继续暂停队列。
- Node 队列即使没有下一条排队消息，也核对明确接收过的等待轮次；确认完成后清理 awaitingTurnId，释放失真的执行占用。每次最多做 2 次历史核对，优先排队消息并按上次核对时间公平调度；人工暂停、送达不明、失败与中断仍受既有保护。

## 回归与边界

- `eventStream.test.ts`：跳号、处理失败、非法帧、重复快照、旧连接失效。
- `followedSessionHistorySync.test.ts`：无错误通知的静默流、接收占位、漏完成、冷加载/回退不误报未读、错误退避、手动核对、暂留会话。
- `codex-followups.test.ts`：无后续消息也清理完成等待；不重复发送，保留暂停与竞态保护。
- `session-state-recovery.spec.ts`：启动独立 HTTP/HTTPS SSE 测试服务，通过浏览器原生 EventSource 接收分帧内容，不直接向 store 注入事件。测试静默连接、漏完成、跳号、读取失败与手动只读重试；覆盖手机/桌面、草稿、未读和阅读位置。

真实前端入口使用当前配置 HTTPS / 8484：`https://10.30.0.24:8484/?mode=session`。浏览器业务 API 为隔离 fixture，SSE 服务使用动态空闲端口并绑定 0.0.0.0；临时证书与服务仅供测试，结束后清理。没有发送真实 Agent 测试任务，没有重启正式 Rust 运行层。

本次聚焦已复现的 Codex 状态链路；共享事件流的保护也覆盖使用它的其他订阅者，不宣称穷尽所有 Agent 协议的状态缺陷。

手动重试会重置本轮等待，并优先于旧在途请求的失败退避；补历史若省略同一轮的 startedAt，保留已观察到的开始时间。两项均用独立失败用例复现后修复。

## 2026-10-08 再次出现发送后不渲染的补查

现场两条消息均已在原生历史中完成，按 clientId 与发送回执对应，最新分页历史可正常读取。没有故障浏览器刷新前的网络记录，不能据此断言当时具体触发条件。

新增故障注入已在真实浏览器复现：首次就绪后让健康检查持续 503，但发送和历史 API 仍可用，同时 SSE 保持连接却不推送正文。旧实现会停止同步器，已送达消息 15 秒后仍无法显示回复。修改同步器生命周期后，同一用例能自动恢复正文、清理占位、更新后台未读，且仅发送一次，保留另一会话草稿。

另一个独立红绿灯用例覆盖运行实例游标从 900 变为 2：旧实现保留 900 导致后续正常事件被丢弃；修复后重新连接不带旧游标，新序号事件直接渲染，无页面刷新、resume 或重复发送。此路径属于排查确认的恢复缺口，不能等同于已经证明此次现场重启过运行服务。

本轮补查验收：`pnpm check` 通过；会话前端 191 个测试文件、668 项测试通过；状态恢复、送达、执行权与状态切换的浏览器联合回归 17/17 通过（2 分钟）。日志为 `.dev-runtime/state-recurrence-check-final.log`、`state-recurrence-session-final.log`、`state-recurrence-browser-acceptance.log`。健康检查故障的浏览器红灯保存在 `state-recurrence-browser-red.log`，生命周期与游标红灯分别在 `state-recurrence-health-red.log`、`state-recurrence-cursor-red.log`。

验收期间修正了测试准备中的两个判断：送达测试必须先通过关注操作创建标签，避免依赖异步项目列表；无刷新检查使用 `performance.timeOrigin`，避免将页面内路由变化计为文档刷新。生产修复仅涉及本项目前端工作台生命周期与事件流处理，未改 Codex 本体、未重启正式运行服务。
