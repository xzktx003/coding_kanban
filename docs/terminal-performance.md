# 终端看板卡顿排查（2026-10-13）

## 现象和已确认的问题

用户反馈长期打开后操作、输入卡顿，占用有突然升高再下降的现象，刷新前端暂时恢复。

1. 终端列表约每秒接收一次快照。仅心跳时间改变也会让所有可见卡片及摘要、菜单重新渲染。父组件不稳定的操作回调进一步使卡片无法跳过无关更新。
2. 每个终端输出帧都安排一次零延时焦点检查。突发输出会创建重复任务；已执行的 timeout 和 RAF 编号仍留在数组中，直到终端卸载才释放。

短时真实只读采样看到周期性 50～90ms 主线程长任务。30 秒 CPU profile 中，卡片及其子树是主要应用代码开销，主要时间消耗在开发模式的 React 元素创建。采样时只有轻量卡片预览，没有网格 xterm 多实例。

## 修复边界

- `AgentGridCard` 缓存只忽略心跳字段；`lastOutputAt` 仍按任务 15 秒、Git 60 秒刷新。输出、连接、交互、分组、回调和其它元数据变化仍使卡片更新。
- 复用完整 JSON 比较，保留 `stabilizeSessionList` 的全部元数据语义。操作回调读取已提交的最新会话；没有剔除注册表字段。
- WebSocket 快照作为 React transition 更新，使输入和显式操作可以打断后台渲染。单纯清理缓存列表而未删除元素时返回原数组。
- 焦点检查合并为单个待执行任务；跟踪集合仅持有尚未执行的 timeout／RAF。卸载继续取消未执行任务，不改变终端输出、输入所有权和回放协议。

## 验证

独立浏览器上下文，API／WebSocket 夹具与真实终端隔离：

- `tests/e2e/terminal-heartbeat-render.spec.ts`：13 张卡片连续 10 次心跳无需卡片正文重绘；修改一张卡片的预览仍更新；每 25ms 推送输出时搜索内容、过滤结果和最终预览正确。
- `tests/e2e/terminal-preview.spec.ts`：8 帧突发输出的焦点定时器数量旧实现为 8（红），修复为 1（绿）；仍接受输入，返回网格后待执行回调被取消。
- 卡片比较单测保留摘要时间桶、任意元数据、传输信息、分组和回调更新边界。

最终结果：`pnpm --filter web test:terminal` 537 项通过，直接相关浏览器回归 7 项通过，`pnpm --filter web build` 通过。浏览器回归也覆盖重连输入、双窗格实例保留、未读完成状态和重启后的分组；双窗格用例补上选择布局后正常按 Escape 关闭菜单的前置步骤。

现场采样地址为 `https://10.30.0.22:8484`（HTTPS，仅本次环境记录，未写入产品默认配置）。修复后短时采样的卡片开销下降，但现场可见卡片数量也发生变化，因此不报告直接性能改善百分比。

## 尚未证明的部分

占用升高后下降可能含垃圾回收，但尚未拿到用户发生卡顿时的设备内存／磁盘指标，也未复现该设备的完整长时间过程。定时器编号积累是真实缺陷，不能据其数量解释全部内存峰值；本次没有完成新的长时间 RSS 验收。

隐藏会话模式的隔离复核显示：隐藏 70 秒后正文已进入 dormant 并释放，后台历史请求没有重新填回正文。因此保留现有后台完成／审批事件、内存治理和 60 秒正文释放链路，不停止这些服务来掩盖卡顿。


## 2026-10-14：所有实时终端同时卡住的继续排查

用户确认上一轮修复后仍卡顿，页面中所有终端一起受影响，内存升高发生在打开网页的设备上。`perblock` 的实际 tmux 窗口包含三个 Codex 窗格，但这是一个浏览器终端展示的 tmux 窗口，不能将它误计为三个 HTTP 流。

### 已复现的连接池阻塞

WebSocket 失败后，旧前端为每个终端保留一个 HTTP 长连接。在真实 Chromium HTTP/1 连接池中，六条同源流可以占满连接：普通 `/api/health` 请求等待超过两秒，释放一条流后才成功；输入和尺寸调整也共用这个源。仅用 Playwright `route.fulfill()` 返回内容会绕过真实连接池，无法验证这个故障。

`tests/e2e/terminal-http-pool.spec.ts` 使用实际 HTTP/1 fixture server，只代理前端静态资源，全部终端与输入均为隔离夹具。八屏下旧实现的 health 请求超时（红灯）。修复后八个终端共用一条回退流，输入 POST 保持可用；退出／重新进入时释放旧连接及订阅。

### 共享回退协议

- `GET /api/terminal-stream`：页面共享的 NDJSON 流。首帧为 `{type: "ready", streamId}`，空行是心跳。
- `POST /api/terminal-stream/:streamId/subscriptions`：提交 `{subscriptionId, agentSessionId, replayBytes}`。每个显示使用者都有独立 ID 和有界 replay，即使它们观察同一个终端。
- 输出帧为 `{type: "frame", subscriptionId, agentSessionId, frame}`。内部 `frame` 沿用现有终端输出／replay／replay-complete 协议。
- `DELETE /api/terminal-stream/:streamId/subscriptions/:subscriptionId`：仅释放该显示订阅。唯一订阅 ID 防止快速关闭后重新打开时，旧 DELETE 误删新订阅。
- 最后一个观察者离开即取消底层 GET。整个流断开时清理所有订阅，由各终端既有重连策略恢复；某个终端不存在只影响该订阅。
- 首帧分派前通知 `onOpen`；旧流和已取消订阅的迟到响应不得投递到新显示实例。服务端限制订阅数与待发送数据，关闭时同时释放定时器和 PTY 输出监听。
- 现有 WebSocket 与旧单终端 HTTP 路由保留，输出订阅／replay 实现共用。

这些订阅只控制网页观察连接，关闭网页流不会终止 Codex、PTY 或 tmux 窗格。

### 慢设备输出队列的容量限制

`TerminalView` 的待绘制字符串数组原来没有容量限制。即使网络正常，只要到达速度长期超过 xterm 绘制速度，就会保留越来越多输出。现在每个实例同时限制待完成字符数（1 Mi 字符）和 chunk 数（1024），包含已经交给 xterm 但回调尚未完成的数据；512 KiB 初次 replay 仍可正常进入队列。

达到上限时暂停该显示的输入、断开显示传输，延迟 750ms 重建本地 xterm，并按既有 replay 协议恢复。不会从 ANSI 流中随意删掉中间片段后继续写进旧解析器；卸载和迟到回调不会重新启动已关闭的显示。服务端发送队列预算为 8 MiB，覆盖合法 replay 的 JSON 转义开销，慢连接超过预算后关闭显示连接。

这修复了可验证的无界队列漏洞。它仍不代表已复现用户设备上的全部内存增长；有界滚动 replay 也不能等同于完整的终端状态快照。

### 现场输出压力采样及限制

本次真实 `perblock` 只读采样中，拦截所有输入和 resize，120 秒内 JS heap 约 12–20 MB，没有复现不断扩大的写入积压。将捕获的实际输出以约 20–40 倍观察速率回放，并对 Chromium 做六倍 CPU 降速，120 秒处理约 34 MB，heap 约 15–30 MB、renderer RSS 约 225–274 MB。这些数据属于隔离浏览器采样，不能代替用户设备上的长期验收，也不能据此认定用户报告的内存暴涨已消失。

真实终端输出捕获只保存在本机临时文件，不纳入仓库。正式浏览器回归使用无用户内容的合成输出。
