# 终端看板卡顿排查（2026-10-13）

## 现象和已确认的问题

用户反馈长期打开后操作、输入卡顿，占用有突然升高再下降的现象，刷新前端暂时恢复。

1. 终端列表约每秒接收一次快照。仅心跳时间改变也会让所有可见卡片及摘要、菜单重新渲染。父组件不稳定的操作回调进一步使卡片无法跳过无关更新。
2. 每个终端输出帧都安排一次零延时焦点检查。突发输出会创建重复任务；已执行的 timeout 和 RAF 编号仍留在数组中，直到终端卸载才释放。

短时真实只读采样看到周期性 50～90ms 主线程长任务。30 秒 CPU profile 中，卡片及其子树是主要应用代码开销，主要时间消耗在开发模式的 React 元素创建。采样时只有轻量卡片预览，没有网格 xterm 多实例。

## 修复边界

- `AgentGridCard` 缓存只忽略心跳字段；`lastOutputAt` 仍按任务 15 秒、Git 60 秒刷新。输出、连接、交互、分组、回调和其它元数据变化仍使卡片更新。
- 复用完整 JSON 比较，保留 `stabilizeSessionList` 的全部元数据语义。操作回调读取已提交的最新会话；没有剔除注册表字段。
- WebSocket 快照作为 React transition 更新，使输入和显式操作可以打断后台渲染。单纯清理缓存列表而未删除元素时返回原数组。
- 焦点检查合并为单个待执行任务；跟踪集合仅持有尚未执行的 timeout／RAF。卸载继续取消未执行任务，不改变终端输出、输入所有权和回放协议。

## 验证

独立浏览器上下文，API／WebSocket 夹具与真实终端隔离：

- `tests/e2e/terminal-heartbeat-render.spec.ts`：13 张卡片连续 10 次心跳无需卡片正文重绘；修改一张卡片的预览仍更新；每 25ms 推送输出时搜索内容、过滤结果和最终预览正确。
- `tests/e2e/terminal-preview.spec.ts`：8 帧突发输出的焦点定时器数量旧实现为 8（红），修复为 1（绿）；仍接受输入，返回网格后待执行回调被取消。
- 卡片比较单测保留摘要时间桶、任意元数据、传输信息、分组和回调更新边界。

最终结果：`pnpm --filter web test:terminal` 537 项通过，直接相关浏览器回归 7 项通过，`pnpm --filter web build` 通过。浏览器回归也覆盖重连输入、双窗格实例保留、未读完成状态和重启后的分组；双窗格用例补上选择布局后正常按 Escape 关闭菜单的前置步骤。

现场采样地址为 `https://10.30.0.22:8484`（HTTPS，仅本次环境记录，未写入产品默认配置）。修复后短时采样的卡片开销下降，但现场可见卡片数量也发生变化，因此不报告直接性能改善百分比。

## 尚未证明的部分

占用升高后下降可能含垃圾回收，但尚未拿到用户发生卡顿时的设备内存／磁盘指标，也未复现该设备的完整长时间过程。定时器编号积累是真实缺陷，不能据其数量解释全部内存峰值；本次没有完成新的长时间 RSS 验收。

隐藏会话模式的隔离复核显示：隐藏 70 秒后正文已进入 dormant 并释放，后台历史请求没有重新填回正文。因此保留现有后台完成／审批事件、内存治理和 60 秒正文释放链路，不停止这些服务来掩盖卡顿。
